# Car factory builder (Blender)

One Blender script builds the car plant twin, at true scale and with every bindable mesh named, and exports `car_factory_updated.glb` for the twin viewer. The layout, coordinates and mesh names are in [`docs/factory-floor-plan.md`](../docs/factory-floor-plan.md).

## Run it

Blender 4.2 or newer; built and verified on Blender 5.2 LTS. No add-ons, downloads or Python packages: everything, textures included, is generated by the script.

**In Blender.**
1. Open the Scripting workspace.
2. Choose Open and select `build_car_factory.py`, then Run Script.
3. The script clears the scene (including the default cube, camera and light), builds the plant and writes `out/car_factory_updated.glb` next to the script.

**Headless.**

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P blender/build_car_factory.py -- --quality final
```

Options after `--`:

| Option | Effect |
|---|---|
| `--quality final` | Default. Full textures, GPU ambient-occlusion bake of the floors (Cycles, about 15 s on an RTX 5060). Whole build about 35 s |
| `--quality draft` | No bake, smaller floor textures. About 8 s |
| `--out DIR` | Output folder (default `blender/out`) |
| `--no-export` | Build the scene only |
| `--no-bake` | Skip the floor bake |
| `--save-blend` | Also save `car_factory_updated.blend` |
| `--only site,press,robot` | Build some zones only: `site`, `press`, `robot`, `pressline`, `body`, `paint`, `assembly`, `logistics`, `utilities`, `people` |
| `--press FILE`, `--robot FILE`, `--fence FILE` | Use your own models (below) |

Outputs in `blender/out/` (gitignored):
- `car_factory_updated.glb`, the twin
- `car_factory_updated.registry.json`, every named mesh with its label, zone, machine, tags and suggested channel
- `textures/`, the generated images

Upload the `.glb` from the asset page in the app as the asset's converted file.

## Your own downloaded models

Set `USER_ASSETS` at the top of `build_car_factory.py`, or pass `--press`, `--robot`, `--fence`. Supported formats are `.glb`, `.gltf`, `.obj`, `.fbx`, `.stl` and `.usd`.

Each model goes through the same steps:
1. Imported.
2. Every part's origin reset to its own geometry.
3. Scaled to its real-world size (press 6.4 m tall, robot 2.6 m tall, fence panel 2.2 m tall).
4. Stood on the floor at the planned position and heading.
5. Flattened, with transforms baked in and no parent nodes.
6. Renamed to upper case.

`ASSET_RENAME_RULES` maps part names to binding names by keyword. For example, a part called "motor" becomes `PRESS_MAIN_MOTOR` and "lube" becomes `PRESS_LUBE_UNIT`; anything unmatched becomes `PRESS_PART_001` and so on. Edit the rules to suit your files.

A fence panel is repeated along the robot cell's perimeter. A model whose front is not the usual one needs its heading changed in `LAYOUT`. The commented import lines near the top show the manual equivalent.

`tests/test_user_assets.py` proves this with deliberately awkward stand-ins: centimetre units, origins metres away from the geometry, yawed and nested parents, and an OBJ.

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P blender/tests/test_user_assets.py
```

## How the code is organised

`parts/*.py` are the source and run in one shared namespace, in file order. `build_car_factory.py` is generated from them by `python blender/bundle.py`, so edit the parts, then bundle. `dev_run.py` runs the parts in place, so tracebacks name the part file. Without the floor bake, the two produce byte-identical files, and the build is deterministic; the GPU bake adds sub-pixel noise to the floor textures only.

| Part | Contents |
|---|---|
| `00_core` | Arguments, scene clearing, unique upper-case names, the mesh registry |
| `10_geo` | Geometry kernel: numpy primitives with analytic normals (rounded boxes, lathes, sweeps, prisms), mesh builder, `Machine` (named hero parts or merged scenery), instancing |
| `15_kit` | Text, hulls, bolt rings, handrails, caged ladders, stairs, grating, signs |
| `20_materials`, `30_textures` | glTF-safe PBR palette; numpy-generated tiling textures |
| `40_site`, `45_floor` | Layout constants, portal frames, walls, services, crane, yards; floor paint and contact shadows rasterised into the floor textures |
| `50_press`, `55_robot`, `56_fence`, `57_car` | Stamping press, six-axis robot with IK, ISO 14120 fencing, lofted car bodies for every production stage |
| `58_props` | Racks, coils, dies, pallets, forklifts, AGVs, tugger trains |
| `60` to `66` | The zones: robot cell, press shop, body shop, paint shop, assembly, outside, people |
| `70_user_assets` | Importing and placing your own models |
| `80_bake`, `90_export`, `99_main` | Floor ambient-occlusion bake, glTF export and registry, the build order |

## Rules the output keeps

These are checked by the app's viewer and by the [Khronos glTF validator](https://github.com/KhronosGroup/glTF-Validator), which reports 0 errors and 0 warnings.

**Mesh names**
- Every mesh name is unique, upper case `A-Z 0-9 _`, and single-material. three.js strips `[ ] . : /` from names, and the viewer binds by name.
- Instanced cars and machines are placed as one node per material for the same reason: a shared multi-material mesh gives its instances identical child names.

**Format and compression**
- No Draco or meshopt compression: the viewer's loader would fetch decoders from a CDN.
- Bare metals keep metalness at or below 0.7. The viewer lights with lamps and no environment map, and a fully metallic surface would render black there.

**Colour and budget**
- Bindable parts use neutral colours, so the viewer's selection, warning, alarm and agent tints stay visible.
- File under 30 MB (upload limit 50 MB), rendered triangles about 1.3 million.
